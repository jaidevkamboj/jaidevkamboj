<details>
<summary><b>💻 Real-time-safe biquad (C++)</b></summary>
<br>

```cpp
// Transposed direct form II — 2 state variables, no allocation, no branches in the loop
struct Biquad {
    float b0 = 1, b1 = 0, b2 = 0, a1 = 0, a2 = 0;   // a0 normalised to 1
    float z1 = 0, z2 = 0;

    inline float process (float x) noexcept {
        const float y = b0 * x + z1;
        z1 = b1 * x - a1 * y + z2;
        z2 = b2 * x - a2 * y;
        return y;
    }
};

void processBlock (juce::AudioBuffer<float>& buffer, juce::MidiBuffer&) override {
    juce::ScopedNoDenormals noDenormals;              // flush denormals on the audio thread
    for (int n = 0; n < buffer.getNumSamples(); ++n) {
        const float g = gainSmoothed.getNextValue();   // click-free parameter changes
        for (int ch = 0; ch < buffer.getNumChannels(); ++ch) {
            auto* x = buffer.getWritePointer (ch);
            x[n] = filters[ch].process (x[n] * g);
        }
    }
}
```

</details>

<details>
<summary><b>🔬 From paper to plugin — my DSP workflow</b></summary>
<br>

1. **Prototype** the algorithm in MATLAB or Python and plot the response.
2. **Create golden vectors** — impulse, sine sweep, noise and edge cases.
3. **Port to C++** with fixed buffers and no allocation in the hot path.
4. **Validate** the C++ output against the golden reference with a numeric tolerance.
5. **Profile** worst-case CPU per block, then optimise (SIMD, oversampling ratio, FFT size).
6. **Listen and measure** in a real host before release.

</details>

<details>
<summary><b>📐 Design principles</b></summary>
<br>

- **Separate hardware from logic.** A thin HAL boundary lets the core run (and be tested) on a PC.
- **Static over dynamic.** Fixed-size buffers and pools beat the heap on constrained targets.
- **Explicit state machines** for protocols, power modes and error handling instead of tangled flags.
- **Measure first.** Cycle counters, scope toggles and trace before any optimization.
- **Fail safe.** Watchdogs, timeouts and defined fallback states for every external dependency.
- **Readable beats clever.** Document the *why* with Doxygen and short design notes.

</details>

<details>
<summary><b>🔬 Typical debugging workflow</b></summary>
<br>

1. Reproduce reliably, then shrink the failing case.
2. Check the physical layer first: power, clocks, pull-ups, signal integrity.
3. On a HardFault, inspect CFSR, HFSR, BFAR and the stacked PC.
4. Use GDB over SWD with watchpoints for corruption; trace for timing issues.
5. Add a regression test or assertion so the bug stays fixed.

</details>
